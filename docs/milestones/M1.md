## Part 1 · The first working version

Owner: Aman Panigrahi (tasks 1, 2, 3 and 5); Vipin Mourya (task 7).

### Task 1 · User, task and success check

Our user is the IT administrator of a 250-person company. Requests arrive all day on the help desk's channel: Jira write access, a new starter, an ended contract, "the same access she has". Today the administrator looks each person up, checks the role policy, changes groups by hand, chases the manager when the policy says so, and replies. They want routine requests done without them, and the rest prepared so that deciding takes a minute, not a quarter of an hour.

Our core task is *processing today's access requests*, as far as it goes without a manager's answer. A case is one request from an employee or the HR feed, or one question or instruction from the operator. The use cases: a grant the role allows (U1); onboarding (U2); offboarding (U3); a non-standard request (U4: "same access as", on someone's behalf, a vague system, a sensitive group); the operator's questions (U5); and the operator's bulk changes (U6).

"Done" is read from the sandbox and the console, never from the agent's report: memberships stamped with the run, pending records, notices, the request's status and the operator's answer. Five of the seven checks also fail a run that changes more than its case needs (t02 and t03 check only the person in the case).

### Every write keyed (task 5)

**The key** is derived by the registry, never by the model (slide 38):

`key = sha256(json([stamp, plan_step or "-", tool, {each effect argument: its canonical form}]))[:32]`

The stamp is the run's ID (in the app, the console session's); arguments are canonicalized: spaces trimmed, IDs upper-cased, the rest lower-cased (`agent/registry.py: derive_key`). Only arguments naming the effect are in it, never the model's text, so one effect in one run is one write. Where that is wrong is in the table below.

| Tool | In the key | Left out |
|---|---|---|
| `access_grant`, `access_revoke` | employee, group, request | expiry, reason |
| `access_revoke_all` | employee, request | reason |
| `access_propose_change` | action, employee, group, request | reason |
| `reply_draft` | recipient, request | the body: a reworded draft must not make a second record |
| `manager_confirmation_draft` | employee, group, request | the body |
| `requests_set_status` | request, status | the note |
| `notices_send_template` | thread, request, template | the rendered text |
| `credentials_issue` | employee, system | — |
| `credentials_record_handover` | employee, credential | — |

| Where the key is checked | How | What could still go wrong |
|---|---|---|
| at the target: the identity API and the pending records | the mock identity API accepts each key once and returns the first result to a repeat (`sandbox/access.py`, the `identity_keys` table); pending records have a unique key (`sandbox/pending.py`) | in the app, every write of one console session carries its stamp, so one effect is one write across the whole session. That is wrong for two tools: a group granted again on the same request after its removal gets the first grant's result back and no membership (`access_grant`), and a second bulk change can get the first one's note to the same manager back, not a new one (`reply_draft` has no request there). No test task does either in one run (CHANGES.md, "Limited") |
| before execution: notices, because the channel takes no key (slide 39) | `sandbox/notices.py` keeps each send's key in `notices_sent`, then reads the thread for the same text from this run (in the app, this console session) before `channel.send` | a second process on the same request, such as two console tabs, could send the same notice; a run is one process, so not in `run.py` |

Tests: a grant repeated under its key or retried after a transient failure leaves one membership (`tests/test_registry.py`); a reworded draft makes one record (`tests/test_tools.py`); a notice sent twice is one message (`tests/test_sandbox.py`).

|---|---|---|

| `access_propose_change` | `pending.by_request(request)` holds the record, open | the same |
| `reply_draft` | `pending_actions` holds a draft for (recipient, request) under our key | the operator is told the draft is missing; nothing is sent either way |
| `manager_confirmation_draft` | `pending_actions` holds a record of that kind | the same |
| `requests_set_status` | `requests.get(id)` has the status | the operator sees the request's last confirmed status on `/` |

| `credentials_record_handover` | `pending.by_request(request)` holds an open `credential_handover` for the credential | the workflow stops with the request left for the operator, who sees the credential on `/people/{id}` |
