### Task 7 · Actions, the approval line and the trifecta

Owner: Vipin Mourya.

The action table is the tool table in Part 3: its columns up to "Grid" answer Lecture 1's question, "What happens when it is wrong, and can we undo it?" (slide 39), for every action, reads included.

**The approval line.** From easiest to undo to hardest, our actions are: every read; setting a request's status; writing a pending record; issuing a new starter's credential into the store; removing a membership the HR feed or the operator asked us to remove; granting a group the role policy allows without a manager; and sending a template notice to the requester. **The line sits below the template notice.** A notice cannot be recalled, so slide 37 would put it under "approve first". We let it go out alone for three reasons: it reaches one person, our code writes every word of it from a fixed template and the request's own records, and it carries nothing private beyond the requester's own request.

Below the line, a person approves first:
- a grant that needs the manager or is high sensitivity: it can be revoked, but what was done with the access meanwhile stays done;
- any reply whose text the model wrote: slide 37 puts a leaking reply under "do not automate";
- asking the manager to confirm (Milestone 2's);
- any message carrying a credential: for this, no tool exists at all.

Each of these, except the last, is prepared as a pending record (`access_propose_change`, `reply_draft`, `manager_confirmation_draft`) that the operator acts on by hand on `/pending`. A drafted reply goes out as the operator's message. No tool the agent holds does an action below the line.

**The trifecta (slide 49).**
- *Untrusted input:* requests and the HR feed on the outside channel, seeded by `sandbox/seed.py` and read by the router and the agent loop, always labelled as the requester's text.
- *Private data:* the directory, memberships and credentials, in `sandbox/directory.py`, `sandbox/access.py` and `sandbox/credentials.py`, reached through `agent/tools/impl.py`.
- *A way out:* template notices through `sandbox/notices.py` to `channel.send`, and drafted replies the operator sends from `app/product.py`, a way out with a person before it.

We narrowed the private-data leg, since no tool returns a secret, but we did not remove it. The agent reads names, roles and group memberships, and a drafted reply could carry them out. All three legs are present by design; the final submission's security work deals with them.

### The plan (task 1)

**U6, the operator's bulk change: yes (`plan.bulk_change: on`).** Once the operator says "remove all access for contractors whose contract ended before today, and draft a note to each one's manager", the steps can be written down. Something also uses the plan after it is written. The validator stops a bad step before any access is removed, the checkpoint catches the one fact the planner could not see (a protected group), and the diff shows afterwards whether every removal ran. A wrong removal locks someone out, so this is where a plan is worth its cost. In my Assignment 2 the bounded agent repeated an exact call in 6 of 18 runs and the planned runs in 0 of 18, and the plan took 29.1% of a planned run's tokens (Vipin's and Aman's runs: 1 and 4 repeats against 0, overheads of 24.5% and 24.6%; `shruti072003/agentic-ai-assignment2/reports/LAB_02.md`, lines 83–95).

**U4, a non-standard request: no.** Its input is a stranger's text, which the planner must not see, so no plan can be written before untrusted text arrives. Each lookup also decides the next (who "Priya" is, then her groups, then which of them Leo's role allows), so a plan written first would be wrong or revised at every step (slide 17). It is cheaper to do than to plan, so it stays on the bounded loop. U5 is the same: an investigation.

**How it is built.** The planner writes the whole plan through one strict tool, `submit_plan` (`agent/plan_schema.json`: every field required, no unions). Each step names its tool, its arguments, the steps it depends on, and an outcome a program can check. The planner sees the instruction, the tool list, and IDs and counts our code reads from the sandbox, never group names or a stranger's text. A note's body is `"$fill"`, and each `fill` line in the trace records what was filled in. The plan is logged before the first tool call.

The validator checks the schema, that every tool exists, that no step depends on a later one, that every step has an outcome, the step limit, and that only employees the planner was given appear. A failing plan is re-planned at most twice (`MAX_REPLANS = 2`), then the run ends `plan_rejected` with nothing run and nothing stamped. **The step limit is 4 per person, capped at five people (20).** That is each person's membership listing, removal, possible proposal and manager's note. It is above the loop's 14 because a plan over many records needs more steps, and I capped it because more than five people should be split by the operator. The orphan check flags a read whose result nothing later uses. Writes are not flagged, since their effect is the point.

**The checkpoint:** after each membership listing, our code fails `protected_memberships_have_a_step` if a membership is in a protected group and no later step proposes removing it, only then may the plan change. In t06 it fails on Victor Lam's legal hold. The reviser sees step results (statuses, counts, IDs) and that reason, never changes a done step, and its plan must pass the same validator. It gets two revisions a run (`MAX_REVISIONS = 2`), then `revision_bound`. I kept one checkpoint, on a fact the planner could not know, because in my Assignment 2 runs passed 10 of 14 with no revision, 5 of 15 with one and 4 of 25 with two. Revising only helps where the check fails for a real reason.

The executor runs the steps in order and may run, retry a fill once, or halt (`step_halted`). A fill call is offered only its step's tool, so any other call is refused, traced (`off_plan`) and never runs. Every planned run ends with a `plan_diff` line, and every agent-path call goes through the repeat check (`repeat_call`).

### The critique (task 2)

| Outgoing action | Can a check find the error without solving the task? | Does the critic know something the author did not? | Limit and log? | Verdict |
|---|---|---|---|---|
| `reply_draft`: the model writes the words (U4 to the requester, U6 to each manager) | Yes: every group the draft says was granted, removed, kept or is waiting can be looked up | Yes: the identity store and pending records as they are after the tools ran; the author knows only what it meant to do | Yes: 2 rounds, a `critique` event per round | **external** |
| `notices_send_template`: our code fills every fact from the records | No: the facts are the records, so a check would compare the records with themselves | No: nothing new | — | **no critique** |

**`reply_draft`**: external. The check (`agent/critique.py`) reads what the run actually did: the memberships it granted or removed, and its open proposals. It never reads a test task's check. A draft fails if it says a group was granted, removed, kept or is waiting when the records say otherwise; if it leaves out a group or person the case changed; or if it names another request or someone outside the case. The reason names the fact ("The draft says SYN-GRP-FINREP-WRITE was granted, but it is waiting for approval (SYN-PEND-0001)."), and the author gets it back to revise. **The bound is 2 rounds.** A draft still failing then is never written, and the run ends `critique_held`. Each round writes a `critique` line with its verdict, reason and characters changed. Both U4's loop and U6's executor draft through this tool, so both are checked.

**`notices_send_template`: no.** Our code fills every fact from the records into a fixed template, so a check would compare the records with themselves. I also left out self-critique, since the author rereading its own draft learns nothing new (slide 34). My Assignment 2 agrees: the external check cost 6.0% of a run's tokens against 18.4% for self-critique, and fixed 2 drafts while breaking none in 18 runs.

**Effort.** gpt-4.1-mini is not a reasoning model, and the starter sends no thinking setting to this vendor (`effort: null`), so it runs at its default. We added no "think step by step" line.

### Errors a model can repair from (task 4)

- **Routing by class (slide 34).**
  - A *protocol error* is for us. That is an unknown tool, a tool the caller may not use, or arguments that are not an object. It is logged as a `protocol_error` event, and the model gets a short generic answer: "No tool by that name ran. Use only the tools in your definitions." A second protocol error in one turn ends the loop with `protocol_error`. We answer the first rather than ending the run because one wrong name costs a turn, while ending would cost the whole case.
  - A *tool execution error* goes to the model, flagged `is_error`. That is the tool ran and failed, or the boundary rejected an argument's value.
- **The repair fact (slide 35).** It comes first and is capped at 400 characters. It says what was wrong, what would be right, and whether a retry can work: "Cannot grant SYN-GRP-PAYROLL-ADMIN to SYN-EMP-0031: SYN-GRP-PAYROLL-ADMIN is high sensitivity. Use access_propose_change with action "grant" instead, for the operator to approve. A retry of this call will fail the same way." **TO FILL with the rewrite:** the closest valid value (similar group or employee IDs) and today's date in the errors that need them.
- **Who retries (slide 36).** A transient failure is retried in code, up to 3 attempts with a backoff of 0.05 s then 0.1 s, before the model sees it (`agent/registry.py`, `tests/test_registry.py`). A failure of meaning goes to the model, which must fix the call. Its retries count against the agent path's step limit (Part 1, task 5).

### Every write keyed (task 6)

**The key** is derived by the registry, never by the model (slide 38):

`key = sha256(json([stamp, plan_step or "-", tool, {each effect argument: its canonical form}]))[:32]`

The stamp is the run's ID, or the console session's ID in the app. The canonical form of an argument trims its spaces, upper-cases IDs and lower-cases everything else (`agent/registry.py: derive_key`). The effect arguments are only those that name the effect, never text the model writes:

| Tool | In the key | Left out |
|---|---|---|
| `access_grant`, `access_revoke` | employee, group, request | expiry, reason |
| `access_revoke_all` | employee, request | reason |
| `access_propose_change` | action, employee, group, request | reason |
| `reply_draft` | recipient, request | the body: a reworded draft must not make a second record |
| `manager_confirmation_draft` | employee, group, request | the body |
| `requests_set_status` | request, status | the note |
| `notices_send_template` | thread, request, template | the rendered text |
| `credentials_issue` | employee, system | — |

Two writes with the same effect in one run are one. That is right for every tool here. Setting the same status twice in a run is one change, and a revised draft replaces nothing, because a draft the critique rejects is never written.

**Where the key is checked.**
- At the target, for the identity API and the pending records. The mock identity API accepts each key once and returns the first result to a repeat (`sandbox/access.py`, the `identity_keys` table). Pending records have a unique key (`sandbox/pending.py`).
- Before execution, for notices, because the channel takes no key (slide 39). `sandbox/notices.py` keeps each send's key in `notices_sent`, then reads the thread for the same text from this run (in the app, this console session) before `channel.send`.
- What could change between that read and the send: a second process handling the same request, such as two console tabs on one request, could send the same notice. A run is one process, so this cannot happen in `run.py`.

Tests: a grant repeated under its key, and one retried after a transient failure, each leave one membership (`tests/test_registry.py`). A reworded draft makes one record (`tests/test_tools.py`). A notice sent twice is one message (`tests/test_sandbox.py`).

### Did the effect happen? (slide 43)

One row per write: the read that confirms it from the environment, never from the agent's account, and what we do when that read cannot answer.

| Write | The read that confirms it | When the read cannot answer |
|---|---|---|
| `access_grant` | `access.memberships(employee)` holds the group, not removed, under our key | the request is set `pending_operator`, and the operator's reply says the grant is unconfirmed; the operator checks `/people/{id}` |
| `access_revoke`, `access_revoke_all` | the membership has `removed_at` set; protected groups are listed as kept | the same; the operator is told which removals are unconfirmed |
| `access_propose_change` | `pending.by_request(request)` holds the record, open | the same |
| `reply_draft` | `pending_actions` holds a draft for (recipient, request) under our key | the operator is told the draft is missing; nothing is sent either way |
| `manager_confirmation_draft` | `pending_actions` holds a record of that kind | the same |
| `requests_set_status` | `requests.get(id)` has the status | the operator sees the request's last confirmed status on `/` |
| `notices_send_template` | `channel.messages(thread, run)` holds the text, and `notices_sent` holds the key | never re-sent blind: the operator is told the notice is unconfirmed and can send it by hand |
| `credentials_issue` | `credentials.for_employee(employee)` has a row for the system | the hand-over record is not written; the operator is told |
